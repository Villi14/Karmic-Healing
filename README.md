# Karmic Healing

[**Download on the App Store**](https://apps.apple.com/app/karmic-healing/id6749057269)

iOS + watchOS app that turns the practice described in Diana Stein's *Karmic Healing*
(*Psychic Healing with Spirit Guides and Angels*) into a guided, trackable routine:
step-by-step balancing-energy sessions, a list of requests to the Lords of Karma,
and reminders.

Built with SwiftUI, [The Composable Architecture](https://github.com/pointfreeco/swift-composable-architecture)
and [SQLiteData](https://github.com/pointfreeco/sqlite-data), with the project
generated by [Tuist](https://tuist.dev).

## Getting started

Requirements: Xcode 16 or newer (Swift 6 toolchain) and Tuist 4.x. Currently
developed against Xcode 26.6 / Swift 6.3 and Tuist 4.202.

```sh
# install Tuist if you don't have it
curl -Ls https://install.tuist.io | bash

# resolve SPM dependencies and generate the Xcode project
tuist install
tuist generate
```

`tuist generate` produces `KarmicHealing.xcworkspace` — open that, not the
`.xcodeproj`. Both are generated artifacts; the source of truth is
[Project.swift](Project.swift) plus the helpers under [Tuist/](Tuist/).

Build from the command line:

```sh
tuist build KarmicHealing            # iOS app
tuist build KarmicHealingWatch       # watchOS app
tuist test                           # all unit test targets
```

Note that both app targets use **manual code signing** with the team `KG394T5RF5`
and named provisioning profiles (see the `settings:` blocks in
[Project.swift](Project.swift)). Without those profiles installed you'll need to
switch the targets to automatic signing locally.

## Project layout

```
Project.swift                     target definitions (apps + all modules)
Tuist/
  Package.swift                   external SPM dependencies + product types
  ProjectDescriptionHelpers/
    Feature.swift                 Module helper: framework + optional test target
    Features.swift                the actual module graph
    Project+MainTargetPlist.swift Info.plist values, version/build numbers
KarmicHealing/
  MainTarget/                     app entry point, root reducer, assets, strings
  Features/<Name>/Sources|Tests   one dynamic framework per feature
```

Every feature is a separate dynamic framework declared in
[Tuist/ProjectDescriptionHelpers/Features.swift](Tuist/ProjectDescriptionHelpers/Features.swift).
Adding a module means adding a `case` to `Feature`, a `Module` value in
`Features.swift`, and wiring it into `Project.swift` — the source/resource/test
paths are derived from the feature name by convention.

### Modules

| Module | Purpose |
| --- | --- |
| `Common` | Design constants, shared views, SwiftUI extensions, and the `AudioClient` / `NotificationClient` / `UserDefaultClient` dependencies |
| `Resources` | Resource-only framework (colors and shared assets), no sources |
| `Onboarding` | First-launch flow; completion is persisted in user defaults |
| `Home` | Root navigation of the app once onboarding is done |
| `DB` | SQLiteData schema (`RequestsList`, `Request`, …), queries and the Reminders UI |
| `BalancingEnergyList` / `BalancingEnergy` | The three-part guided energy-balancing sessions |
| `AppSettings` | Language, appearance and app-level preferences |
| `TestingUtilities` | XCTest helpers (links XCTest — never depend on it from app modules) |
| `WatchApp` | Self-contained watchOS app with its own clients, models and screens |

The root reducer [KarmicHealing.swift](KarmicHealing/MainTarget/Sources/KarmicHealing.swift)
switches between `onboarding` and `home` destinations at launch. Tests live next
to their modules under `Features/<Name>/Tests` (currently `Home`, `DB`,
`BalancingEnergy`, `TestingUtilities`).

## Dependencies

Pinned to exact versions in [Tuist/Package.swift](Tuist/Package.swift):

- `swift-composable-architecture` 1.26.1
- `swift-navigation` 2.10.3
- `sqlite-data` 1.8.0
- `swift-dependencies` 1.12.0 — pinned below 1.13.0, where `Clocks` moved behind a
  package trait that Tuist ignores, which breaks TCA's re-export
- `swift-snapshot-testing` 1.18.4

They are built as frameworks rather than static libraries (`productTypes` in
`Package.swift`) so the iOS and watchOS targets can share them without duplicate
symbols.

## Localization

The app speaks fifteen languages: `en`, `uk`, `ru`, `es`, `pt-BR`, `fr`, `de`,
`it`, `pl`, `tr`, `zh-Hans`, `ja`, `ko`, `hi` and `bn`. Only the first three have
been read by a person; the rest are machine translations, listed as such in
[Translation.swift](KarmicHealing/Features/Common/Sources/Translation.swift) and
owned up to in Settings to whoever is actually reading them.

The phone reads a string catalog,
[MainTarget/Resources/Localizable.xcstrings](KarmicHealing/MainTarget/Resources/Localizable.xcstrings),
through the `.loc` string extension, e.g. `"skip".loc`. Add every language when
adding a key —
[LocalizationCatalogueTests.swift](KarmicHealing/MainTarget/Tests/LocalizationCatalogueTests.swift)
checks the catalog as it ships: every language present, every key answered in
each, nothing blank, and format specifiers agreeing across translations.

The watch does not read that catalog. It translates by hand from a table in
[String+Localization.swift](KarmicHealing/Features/WatchApp/Sources/Core/String+Localization.swift),
keyed by the very strings its screens ask for, because the language is chosen in
the app rather than taken from the system. Its own tests take the language list
from the picker, so adding a language there is adding a demand for words.

## Versioning

Version, build, display name and App Store category are set in one place —
[Project+MainTargetPlist.swift](Tuist/ProjectDescriptionHelpers/Project+MainTargetPlist.swift)
— and shared by both apps. They are build settings (`MARKETING_VERSION`,
`CURRENT_PROJECT_VERSION`, `INFOPLIST_KEY_…`) so Xcode's General tab shows them,
with the plists referencing the settings. Bump them there and regenerate.
